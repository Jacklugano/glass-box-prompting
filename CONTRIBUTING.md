# Contributing

Thank you for your interest in Glass-Box Prompting. This is an open specification and contributions are welcome.

---

## Ways to contribute

### Report issues or propose changes

Use [GitHub Issues](https://github.com/Jacklugano/glass-box-prompting/issues) to:

- Report errors, ambiguities, or inconsistencies in the specification
- Propose clarifications or additions to the FAQ
- Suggest new examples or sector-specific templates
- Report broken links or outdated references

Please describe the issue clearly and, where applicable, propose specific replacement text.

### Propose specification changes

Substantive changes to the specification (new principles, modified definitions, structural changes) require more context. When opening an issue for a specification change, include:

1. **What** you propose to change and where (section number, current text)
2. **Why** the current text is insufficient or incorrect
3. **What** the proposed replacement text is
4. **Whether** the change is backward-compatible with existing v0.2 publications

Changes that affect compliance criteria or founding principles are considered breaking changes and require a version increment.

### Share an adoption case

If you have adopted Glass-Box Prompting in your professional documents and are willing to share a synthetic/anonymized example, open an issue or pull request with your case study following the structure of [examples/electrical-quote-it.md](examples/electrical-quote-it.md).

Particularly welcome: cases from sectors other than electrical installation, and cases from multilingual jurisdictions.

### Domain partnership inquiries

If you are a qualified domain specialist interested in co-authoring a high-stakes domain extension (healthcare, legal, financial — see [ROADMAP.md](ROADMAP.md)), please open an issue describing your background and the domain you are interested in. The author will respond directly.

---

## What this project does not accept

- Pull requests that add imperative AI-directed language to any file in this repository
- Pull requests that embed instructions in document templates (this is the v0.1 pattern, superseded by v0.2)
- Contributions that introduce centralized registries, certification schemes, or compliance authorities — the protocol is intentionally decentralized
- Marketing language or promotional framing in specification files

---

## Pull request process

1. Fork the repository and create a branch from `main`
2. Make your changes with clear commit messages
3. Ensure your changes are consistent with the founding principles in [SPECIFICATION.md §3](SPECIFICATION.md)
4. Open a pull request with a description of what you changed and why
5. The maintainer will review and respond

For significant changes, open an issue first to discuss before investing time in a pull request.

---

## Style guide

- **Language**: English for all specification and documentation files
- **Tone**: technical and neutral — spec style, not marketing style
- **Comments**: document the *why*, not just the *what*
- **Examples**: synthetic/anonymized — no real personal data, no real client names or project numbers
- **Links**: use relative links for files within the repository; absolute URLs for external references
